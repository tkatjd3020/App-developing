# 눈박(NunBak) 개발 기획서

> **문서 목적**: 실제 개발을 위한 내부 기획서(로드맵). 팀/외부 설득용이 아닌, 개발 과정에서 스코프와 판단 기준을 잡기 위한 문서.
> **작성일**: 2026-09-09

---

## 1. 프로젝트 개요

### 1.1 배경 및 문제 정의
중·고등학생 및 대학생 밴드부가 합주할 때, 별도의 메트로놈 기기를 구매하지 않고도 휴대폰만으로 편리하게 박자를 맞출 수 있는 방법이 필요하다. 기존 메트로놈 앱들은 각 기기가 독립적으로 동작하기 때문에, 여러 명이 동시에 사용할 때 박자가 서로 어긋나거나 소리가 겹쳐 오히려 방해가 되는 경우가 많다.

### 1.2 타겟 사용자
- 중·고등학교 밴드부
- 대학교 밴드 동아리
- 정기적으로 합주(세션 연습)를 하는 아마추어 밴드

### 1.3 핵심 차별점
| # | 차별점 | 설명 |
|---|---|---|
| 1 | **세션 간 동기화** | 밴드부 멤버들의 휴대폰을 서로 연결해 동일한 박자를 공유 |
| 2 | **시각적 박자 표시** | 동기화 시에는 소리 대신 시각 정보로 박자를 표시 → 연주 소리에 집중하면서도 눈으로 박자 확인 가능 |

> ⚠️ 동기화 상태에서는 오디오 지연(latency) 이슈로 인해 청각적 박자 지원이 불가능함. 이는 제약이 아니라 이 앱의 핵심 설계 전제로 다룬다.

## 2. 핵심 기능 및 MVP 범위

### 2.1 MVP (v1) 포함 기능
- [ ] 단일 기기 메트로놈 기본 기능 (BPM 설정, 시작/정지)
- [ ] 시각적 박자 표시 UI (애니메이션 기반)
- [ ] 2대 기기 간 로컬 네트워크 연결 (호스트-클라이언트 구조)
- [ ] 기기 간 시간 동기화 (박자 오프셋 보정)
- [ ] 동기화 상태에서의 시각 전용 박자 표시

### 2.2 v2 이후로 미룰 기능
- [ ] 3대 이상 다중 세션 동기화 및 관리
- [ ] 세션 생성/참가 UI 고도화 (세션 이름, 비밀번호 등)
- [ ] 박자표(리듬 패턴) 커스터마이징, 박자 세기(강/약) 시각 구분
- [ ] 연습 기록 저장, 히스토리
- [ ] 스토어 출시용 다듬기 (아이콘, 온보딩, 다국어 등)

> 1개월 솔로 개발 목표이므로, **"동작하는 프로토타입/베타"**를 목표로 하고 **"완성도 높은 출시 버전"은 목표에서 제외**한다.

## 3. 기술 아키텍처

### 3.1 프로젝트 조건
| 항목 | 내용 |
|---|---|
| 플랫폼 | 크로스플랫폼 (iOS + Android) |
| 개발 형태 | 혼자 개발 |
| 목표 기간 | 1개월 이내 |

### 3.2 기술 스택 제안
- **프레임워크**: Flutter — 단일 코드베이스로 iOS/Android 동시 개발, 박자에 맞춘 커스텀 애니메이션 구현에 유리
- **연결 방식**: 같은 Wi-Fi 네트워크 내에서 한 기기가 호스트 역할을 하고 나머지 기기가 접속하는 구조 (WebSocket 기반). 별도 서버 인프라 불필요
- **동기화 알고리즘**: Cristian's Algorithm 기반 접근 — 각 클라이언트가 호스트와의 왕복 시간(RTT)을 측정하고, 그 절반을 편도 지연으로 가정해 시계 오프셋을 추정. 완벽하진 않지만 구현 난이도가 낮고, 로컬 Wi-Fi(합주실) 환경에서는 오차가 비교적 작을 것으로 예상

### 3.3 아키텍처 설계 시 고려 사항
- 호스트 기기 장애/네트워크 끊김 시 처리 방안 (MVP에서는 "재접속 안내" 수준으로 단순화 가능)
- 박자 시각화는 프레임 드롭 없이 부드럽게 동작해야 하므로, 애니메이션 성능 확인 필요

## 4. 개발 로드맵 (4주 계획)

| 주차 | 목표 | 세부 내용 |
|---|---|---|
| **1주차** | 단일 기기 메트로놈 골격 | BPM 설정 UI, 시작/정지, 소리·진동 없이 시각 박자 애니메이션 구현 |
| **2주차** | 로컬 네트워크 연결 | 호스트-클라이언트 구조로 2대 기기 연결 (WebSocket), 연결 상태 UI |
| **3주차** | 시간 동기화 구현 | Cristian's Algorithm 기반 오프셋 계산, 실제 두 기기로 오차 실측 |
| **4주차** | 튜닝 및 마무리 | 오차 보정 튜닝, UI/UX 다듬기, 버그 수정 → 베타 테스트 가능 상태로 마무리 |

## 5. 기술적 리스크 및 검증 계획

### 5.1 핵심 리스크
동기화 기능은 이 프로젝트에서 **가장 난이도가 높고 불확실성이 큰 부분**이다. 정밀한 다중 기기 동기화는 숙련된 엔지니어에게도 시간이 걸리는 영역이므로, 1개월 솔로 개발 범위 내에서는 "완벽한 동기화"가 아닌 "실사용에 지장 없는 수준의 동기화"를 목표로 한다.

### 5.2 오차 허용 기준 (직접 정의 필요)
- [ ] 시각적으로 몇 ms까지 어긋나면 사용자가 위화감을 느끼는지 자체 기준 설정
- [ ] 위 기준을 3주차 실측 단계의 검증 목표로 사용

### 5.3 검증 방법
- 실제 기기 2대를 나란히 놓고 시각 박자 애니메이션의 어긋남을 육안으로 확인
- 합주실과 유사한 Wi-Fi 환경(여러 기기 연결, 네트워크 혼잡 상황)에서 반복 테스트
