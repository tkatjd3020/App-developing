# App-developing

## <개요>
1. 중고등학생·대학생 밴드와 세션을 위한 애플리케이션으로, 개인 및 단체 곡 추천과 밴드 합주에 유용한 기능을 제공합니다.

---

## <기능>

### 1. 순위 차트
1. 애플리케이션 초기에는 시드데이터를 이용한 차팅. 후에 애플리케이션 내 자체 데이터가 쌓여가면 자체 데이터의 비중을 늘리는 하이브리드 방식 채택. 초기 데이터 생성은 유튜브 api(youtube data api v3)를 이용해 수집.
2. 밴드 선호 곡 순위차트

   1. 목적
      1. "밴드가 실제로 즐겨 연주하는 곡"을 순위화하여 제공. 개인의 취향이 아닌 밴드 합주 맥락에서의 선호도를 반영하는 것이 핵심 목표.

   2. 데이터 파이프라인 개요
      1. (1) 시드 곡 리스트 확보 → (2) 유튜브 API 통계 수집 → (3) 점수 산출 → (4) 자체 데이터 비중 확대(하이브리드 전환)의 4단계로 구성.
      2. 초기에는 유튜브 API 기반 시드 데이터로 차트를 채우고, 앱 내 자체 행동 데이터가 쌓이면 곡별로 자체 데이터 비중을 점진적으로 확대.

   3. 시드 곡 리스트 확보 (후보 풀 구성)
      1. 후보 풀(내부 관리용)과 차트 노출(사용자 화면)은 분리하여 설계. 후보 풀은 순위 경쟁에 참여하는 전체 곡 집합으로 100~200곡 이상으로 지속 확장하고, 실제 사용자에게 보여주는 차트는 상위 50위로 제한한다.
      2. 1차 시드 (수동 큐레이션)
         1. 운영진이 밴드에서 자주 연주되는 곡 100~200곡을 직접 선정.
         2. 선정 기준: 장르 분포(록/펑크/시티팝/발라드 등), 시대 분포, 난이도 분포, 국내/해외 비율.
         3. 이후 자동 수집 로직의 품질을 검증하는 기준선 역할.
      3. 2차 확장 (반자동 수집)
         1. 밴드 커버 전문 채널의 업로드 목록을 유튜브 API `search.list(channelId=...)`로 수집.
         2. 대학 축제·동아리 공연 영상 검색 후 제목에서 곡명 파싱.
         3. 파싱된 곡명은 즉시 등록하지 않고 검수 큐에 적재, 일정 기준(등장 횟수 N회 이상 등) 충족 시 후보 풀에 편입.
      4. 3차 (사용자 곡 추가 요청)
         1. 사용자가 앱 내에서 특정 곡의 후보 풀 편입을 요청할 수 있는 기능 제공.
         2. 단, 이 요청은 순위 점수에 직접 반영하지 않고 "후보 풀 편입 트리거"로만 사용한다.
         3. 사유: 사용자의 자기 평가(내가 이 곡을 좋아한다)는 실제 선호와 괴리가 있을 수 있고, 특히 자신이 맡은 세션 관점의 선호가 밴드 전체 선호로 오인될 가능성이 있음. 따라서 명시적 요청은 "경쟁 참가 자격"만 부여하고, 실제 순위 반영은 아래 4)의 행동 기반 점수로만 결정한다.

   4. 유튜브 API 데이터 수집
      1. 사용 API: YouTube Data API v3
         1. `search.list`: 키워드로 후보 영상 검색 (영상 ID 확보용, 쿼터 소모 큼)
         2. `videos.list`: 영상 상세 통계 조회 (조회수, 좋아요, 업로드일, 길이, 채널 ID / 최대 50개 배치 조회, 쿼터 소모 적음)
      2. 검색 쿼리 패턴 (예시)
         1. `{아티스트} {곡명} 밴드 커버` / `band cover`
         2. `{아티스트} {곡명} 합주` / `{아티스트} {곡명} 축제 라이브`
      3. 수집 절차
         1. 곡별로 위 쿼리를 `search.list`로 실행하여 상위 N개(10~20개) 영상 ID 확보.
         2. 확보한 ID를 `videos.list`로 배치 조회하여 통계 수집.
         3. 곡–영상 매핑 테이블에 저장.
      4. 노이즈 필터링 및 분리 집계 규칙
         1. 쇼츠(60초 미만) 영상은 제외하지 않고 별도 그룹으로 분리 집계한다. 쇼츠와 롱폼은 알고리즘 노출 편차로 조회수 스케일이 크게 다르므로, 각 그룹 내에서 정규화한 뒤 아래 가중치로 합산한다.
            1. `곡_점수 = 롱폼_점수 × W_long + 쇼츠_점수 × W_short` (W_short는 초기 낮게 설정 후 데이터 기반 조정)
         2. 공식 뮤직비디오·음원 채널 영상 제외 (채널명/제목에 "Official", "MV" 등 포함 시 필터).
         3. 동일 채널 영상은 최대 2~3개까지만 카운트 (특정 채널의 순위 독점 방지).
         4. 지나치게 긴 영상(공연 풀영상 등, 예: 15분 초과)은 제외.

   5. 점수 산출 공식
      1. 기본 형태
         1. `영상_점수 = log(조회수 + 1) × decay(게시일) × 채널중복_보정`
         2. `곡_점수 = Σ 영상_점수` (롱폼/쇼츠 각각 정규화 후 4)의 가중합 적용)
      2. 로그(또는 제곱근) 스케일 적용 근거
         1. 유튜브 조회수는 멱법칙(power law) 분포를 따르며, 소수의 대형 채널 영상이 조회수 총량을 독점하는 경향이 있음.
         2. 로그(혹은 완만한 압축이 필요할 경우 제곱근)를 적용하지 않으면 "채널 인기도"가 "곡 인기도"로 잘못 반영됨 (예: 유명 유튜버 1개 영상 200만 조회 vs 아마추어 밴드 30팀의 각 3만 조회 — 후자가 실제 밴드 사이의 선호를 더 잘 대변함에도 선형 합산 시 전자가 우위).
      3. 시간 감쇠(time decay) 적용 근거
         1. 로그 스케일과는 별개로, 게시일이 오래된 영상일수록 누적 조회수가 유리해지는 문제를 보정하기 위해 시간 감쇠를 함께 적용.
         2. `decay = 감쇠계수^(경과일수/반감기)` 형태 (예: 감쇠계수 0.5, 반감기 30일).
         3. 로그 압축과 시간 감쇠는 서로 다른 문제(조회수 분포 왜곡 vs 시간 경과에 따른 유불리)를 해결하므로 함께 사용.
      4. 채널 중복 보정: 동일 채널 다수 영상 제한(4-4-3)과 연동하여 채널 수 대비 점수 과다 산정 방지.
      5. 보조 지표: 조회수 외에 "서로 다른 채널 수(=커버한 밴드/팀의 수)"를 보조 신호로 활용 검토. 채널 인기도에 오염되지 않는 지표이므로 주 지표를 보완.
      6. 최종 점수는 0~100 스케일로 정규화하여 저장, 이후 자체 데이터 점수와 합산 가능하도록 함.

   6. 세션 편향 보정
      1. 문제 정의: 사용자가 표현하는 곡 선호(좋아요, 추가 요청 등)는 자신이 맡은 세션 파트가 좋아서인 경우가 많아, 특정 세션(예: 기타·보컬) 사용자 비중이 높으면 밴드 전체 선호 차트가 해당 세션 취향으로 왜곡될 수 있음.
      2. 대응 방안
         1. 사용자 행동 데이터를 세션별로 분리 집계한 뒤, 실제 밴드 편성 비율(또는 균등 비율)에 맞춰 가중 평균하여 밴드 차트에 반영. 특정 세션 사용자 비중이 높다고 해서 해당 세션 취향이 과대표현되지 않도록 함.
         2. 명시적 선호 표현(좋아요, 추가 요청)보다 암묵적 행동 신호(실제 합주 녹음 사용, 연주 곡 등록 등)에 압도적으로 높은 가중치를 부여. 사용자의 자기 평가보다 실제 행동을 신뢰도 높은 신호로 취급.

   7. 하이브리드 전환 (시드 데이터 → 자체 데이터)
      1. 자체 데이터 행동 가중치 (예시)

         | 행동 | 가중치(예) | 비고 |
         |---|---|---|
         | 합주 녹음 기능에서 사용 | 10 | 실제 연주까지 이어진 최강 신호 |
         | 밴드 단체방 곡 리스트에 추가 | 5 | 연주 의도 명확 |
         | 개인 "연주 가능 곡"에 등록 | 4 | 실연 경험 반영 |
         | 좋아요/스크랩 | 2 | 관심 표현(자기평가 편향 가능) |
         | 곡 상세페이지 조회 | 1 | 약한 신호 |
         | 곡 추가 요청 | 0 (점수 미반영) | 후보 풀 편입 트리거 전용 |

      2. 최종 점수 = α × 자체데이터_점수 + (1 − α) × 유튜브시드_점수
      3. α(자체 데이터 가중치) 산출: 데이터량 기반 방식 채택.
         1. `α = min(0.8, 해당곡_행동이벤트수 / 임계치)`
         2. 곡별로 α가 상이하게 적용됨 — 인기곡은 빠르게 자체 데이터 중심으로 전환되고, 마이너 곡은 계속 시드 데이터에 의존.

   8. 차트 노출 범위
      1. 사용자 노출 차트는 50위까지로 제한. 순위 하위권(예: 100~200위권)은 표본 부족으로 순위 변동이 통계적으로 무의미해질 수 있어 오히려 신뢰도를 저해함.
      2. 후보 풀 자체는 순위 경쟁 대상 확보 및 개인화 추천 등 타 기능의 곡 DB 역할을 겸하므로 별도로 계속 확장.
      3. (검토 사항) 전체 50위 외에 장르별/난이도별 서브 차트 구성 여부.

   9. 갱신 주기 및 API 쿼터 관리

      | 작업 | 주기 | 비고 |
      |---|---|---|
      | 신규 곡 `search.list` 수집 | 월 1회 | 쿼터 소모 큼(1회 100유닛) |
      | 기존 영상 `videos.list` 통계 갱신 | 주 1회 | 쿼터 소모 적음 |
      | 자체 데이터 집계 및 점수 재계산 | 일 1회(배치) | |
      | 차트 노출 | 실시간(캐시된 점수 조회) | |

      1. 일일 기본 쿼터(10,000유닛) 기준 `search.list`는 하루 최대 약 100회 가능. 곡 1개당 검색 쿼리 4개 소요 시 하루 약 25곡 처리 가능 → 신규 곡 수집은 여러 날에 걸친 배치 분산 처리 필요.

   10. 리스크 및 대응

       | 리스크 | 대응 |
       |---|---|
       | 유튜브 API 쿼터 부족 | 배치 분산, 캐싱, 필요 시 쿼터 증설 신청 |
       | YouTube API 이용약관상 데이터 저장/캐싱 제약 | 출시 전 최신 약관 검토, 원본 통계가 아닌 가공 점수만 저장 |
       | 곡명 파싱 부정확 | 검수 큐 도입, 사용자 신고 기능 |
       | 커버 영상이 적은 곡의 과소평가 | 채널 수 등 보조 지표 활용, 최소 노출 보장 로직 검토 |
       | 초기 자체 데이터 부족 | α를 데이터량 기반으로 설계하여 자연스럽게 완화 |
       | 특정 세션 사용자 비중에 따른 차트 왜곡 | 세션별 집계 후 가중 평균, 암묵적 행동 신호 우선 반영 |

       
3. **세션별 선호 곡 순위차트(보컬, 기타, 베이스, 드럼, 건반)**
   1. 목적
      1. 특정 세션(악기)을 맡은 개인이 "연주해보고 싶어하는" 곡을 세션별로 순위화하여 제공.
      2. 밴드 합주 맥락과 무관한 개인 차원의 연주 욕구를 반영하는 것이 핵심. 곡의 음악적 특성(예: 기타 솔로가 화려한 곡)이 아니라, 그 세션 연주자들이 실제로 찾는 곡을 기준으로 한다.
   
   2. 밴드 선호 곡 차트(2번)와의 관계
      1. 2번 차트는 "사용자의 자기평가는 실제 밴드 선호와 괴리될 수 있다"는 전제 위에 설계되어, 곡 추가 요청·좋아요 같은 명시적 자기평가 신호를 배제하거나 낮게 취급하고 실제 합주 행동을 신뢰한다.
      2. 3번 차트는 정반대로, "연주하고 싶다"는 자기평가 그 자체가 측정 대상이다. 따라서 2번에서 노이즈로 걸러내는 신호가 3번에서는 핵심 신호가 된다.
      3. 같은 사용자 행동을 정반대 방식으로 소비하는 구조이며, 이것이 두 차트의 차별점이자 존재 이유다.
      4. 이 때문에 2번의 행동 가중치 표(합주 녹음=10, 좋아요=2 등)는 3번에 그대로 재사용할 수 없다. 3번은 별도의 스코어링 체계를 갖는다.
   
   3. 대상 세션 및 사용자 세션 소속
      1. 대상 세션: 보컬, 기타, 베이스, 드럼, 건반 (5종).
      2. 사용자는 대표 세션 1개만 지정한다. 한 사용자의 신호는 그 세션 차트에만 반영된다.
      3. 다중 세션(예: 기타+건반 겸업) 지원 여부는 v1 범위에서 제외하고 추후 별도 논의한다.
   
   4. 데이터 소스
      1. 3번 차트를 위해 새로 만들어야 하는 사용자 기능은 없다. 기존에 계획된 기능에서 파생되는 신호를 재활용한다.
      2. 신호 출처
         1. 세션별 추천(설문) 실행 결과 — "2. 개인화 곡 추천 > 세션별 추천"
         2. LLM 자연어 검색 결과 — "2. 개인화 곡 추천 > LLM 자연어 검색을 통한 곡 추천"
         3. 곡 추가 요청 및 조화 판단 기능을 통해 발생하는 곡 관심 신호
      3. 유튜브 시드 데이터는 사용하지 않는다. 조회수는 "누가 봤는지"를 알려주지 않으므로 세션별 선호를 추정할 수 없다. 3번 차트는 자체 데이터만으로 구성된다.
      4. 신호의 두 계층 구분
         1. 프로필 속성(음역대, 보유 악기, 튜닝 가능 여부 등)은 "현재 상태"에 해당한다. 최신 응답이 이전 응답을 덮어쓰며, 누적되지 않고 시간 감쇠도 적용하지 않는다.
         2. 추천 실행 결과로 나온 곡 선택 이벤트는 "누적 로그"에 해당한다. 차트 점수는 이 계층에서 산출되며 시간 감쇠가 적용된다.
         3. 설문이냐 LLM 검색이냐로 나누는 것이 아니라, 프로필 상태냐 곡 선택 이벤트냐로 나눈다. 두 기능 모두 양쪽 계층의 데이터를 만들어낸다.
      5. 곡 추가 요청의 진입 시점
         1. 맥락 없이 "차트에 올랐으면 하는 곡을 적어달라"는 형태의 입력창은 사용하지 않는다.
         2. 대신 조화 판단 기능(개인↔곡, 밴드↔곡의 어울림을 판정)에서 사용자가 궁금한 곡을 입력하는 행위 자체를 관심 신호로 취급한다. 해당 곡이 아직 후보 풀에 없으면 자연스럽게 후보 풀 편입 요청으로 이어진다.
         3. 조화 판단 기능 자체의 설계는 "3. 개인 프로필 > 개인과 개인, 밴드와의 조화점수 계산 기능"과 함께 별도 논의한다.
   
   5. 신호 라우팅 원칙
      1. 동일한 행동이라도 발생한 화면에 따라 목적지 차트가 달라진다.
         1. 개인 화면(개인 프로필, 개인 추천)에서 발생한 곡 관심 신호 → 세션별 선호 차트
         2. 단체방(밴드) 화면에서 발생한 곡 관심 신호 → 밴드 선호 곡 차트
      2. 사용자 입장에서도 "내가 혼자 찾아본 것"과 "밴드에서 같이 찾아본 것"이 구분되므로 직관에 어긋나지 않는다.
      3. 후보 풀은 2번 차트와 공유한다. 곡 추가 요청이 이미 후보 풀 편입 트리거이므로 별도 연동 설계가 필요하지 않다.
   
   6. 점수 산출
      1. 순위 점수는 총 신호량을 기준으로 한다. 동일 사용자의 반복 신호도 그대로 반영한다.
         1. 근거: 같은 곡을 반복해서 찾는 행위는 그 곡(또는 유사한 느낌의 곡)에 대한 선호의 강도를 나타내는 것으로 해석한다.
      2. 시간 감쇠를 적용한다.
         1. 형태는 2번 차트와 동일하게 `감쇠계수^(경과일수/반감기)`를 사용한다.
         2. 반감기는 2번 차트(30일)보다 길게 잡는다. 30일은 유튜브 영상의 초기 조회수 쏠림을 보정하기 위한 값이지만, "이 곡을 연주해보고 싶다"는 욕구는 그만큼 빠르게 식지 않는다. 3~6개월 수준을 검토하되 실제 데이터를 보고 조정한다.
      3. 어뷰징 방지: 한 사용자가 생성할 수 있는 신호의 총량에 상한을 둔다. 반복 신호 자체를 막는 것이 아니라, 악의적 대량 생성이 차트를 조작하지 못하게 하는 것이 목적이다.
      4. 2번 차트의 "세션 편향 보정(밴드 편성 비율 기준 가중 평균)"은 3번에 적용하지 않는다. 3번은 애초에 단일 세션만 보는 차트이므로 보정 대상이 존재하지 않는다.
   
   7. 차트 등재 자격 (하한선)
      1. 서로 다른 사용자 5명 이상이 찾은 곡만 차트에 오를 자격을 갖는다.
      2. 단위를 "신호 수"가 아니라 "사람 수"로 두는 이유
         1. 신호 30개는 30명이 한 번씩 찾은 것인지 3명이 열 번씩 찾은 것인지 구분하지 못한다. 차트 신뢰도 관점에서 이 둘은 전혀 다른 상황이다.
         2. 사람 수를 기준으로 하면 한 사용자가 아무리 많은 신호를 만들어도 혼자서는 곡을 차트에 올릴 수 없다.
      3. 점수와 자격은 서로 다른 단위로 판정한다. 점수(순위)는 총 신호량으로, 자격(등재 여부)은 서로 다른 사용자 수로 결정한다.
      4. 자격 판정에는 시간 감쇠를 적용하지 않는다.
         1. 근거: "5명이 이 곡을 찾았다"는 것은 지나간 사실이며 시간이 흐른다고 사라지지 않는다. 감쇠는 "지금 무엇이 뜨거운가"를 반영하기 위한 장치이므로 순위 점수에만 필요하다.
         2. 따라서 자격은 누적 기준으로 한 번 통과하면 영구히 유지된다.
         3. 오래되어 아무도 찾지 않는 곡이 자격을 유지하더라도 문제되지 않는다. 감쇠된 점수가 0에 수렴하므로 상위 10위 안에 노출되지 않는다.
      5. (향후 검토) 사용자 규모가 커지면 5명이라는 절대값은 상대적으로 무의미해진다. 이때 "5명"과 "해당 세션 활성 사용자의 일정 비율" 중 큰 값을 자격 기준으로 삼는 방식으로 전환할 수 있다. v1은 5명 고정으로 시작한다.
   
   8. 차트 공개 정책
      1. 세션별로 독립적으로 판정한다. 5개 세션 차트가 동시에 열리지 않으며, 표본이 적은 세션(베이스, 건반 등)은 늦게 열릴 수 있다.
      2. 자격을 통과한 곡이 15곡 이상 확보된 세션의 차트만 공개한다.
      3. 15곡을 기준으로 두는 이유
         1. 자격 통과 곡이 정확히 10곡일 때 공개하면, 그 top 10은 "경쟁을 통과한 10곡"이 아니라 "자격을 갖춘 곡이 그것뿐이라 전부 올라간 10곡"이 된다. 순위표의 형태를 하고 있지만 실제로는 아무것도 선별하지 않은 목록이다.
         2. 여유분을 두어야 10위와 11위 사이에 의미 있는 경계가 생긴다.
      4. 데이터가 부족한 세션은 차트를 노출하지 않는다. 급조된 차트를 내보내는 것보다 늦더라도 완성도 있는 차트를 공개하는 것을 우선한다.
      5. 재비공개 규칙은 두지 않는다. 자격 판정에 감쇠가 적용되지 않아 자격 통과 곡 수가 감소하지 않으므로, 한 번 공개된 차트가 조건 미달로 되돌아가는 상황이 발생하지 않는다.
   
   9. 노출 범위 및 갱신 주기
      1. 세션당 상위 10곡을 노출한다.
      2. 자체 데이터가 충분히 쌓이면 노출 범위 확대(20위, 30위 등)를 검토한다. 초기에는 확대할 만한 곡 수 자체가 확보되지 않는다.
      3. 갱신은 2번 차트의 배치 인프라를 그대로 재사용한다(자체 데이터 집계 및 점수 재계산 일 1회, 차트 노출은 캐시된 점수 실시간 조회).
   
   10. 구현 시 선행 요구사항
       1. 곡 관심 신호가 발생하는 모든 지점(추천 실행 결과 선택, 곡 추가 요청, 조화 판단 요청)에서 행위자의 세션 태그를 함께 기록해야 한다. 이 태그가 없으면 신호를 세션 차트로 라우팅할 수 없다.
       2. 신호 발생 화면(개인 / 단체방)을 함께 기록해야 한다. 5번의 라우팅 원칙이 이 값에 의존한다.
       3. 곡별 "서로 다른 사용자 수"를 집계할 수 있도록 신호 로그에 사용자 식별자를 유지해야 한다.
   
   11. 미결 항목
       1. UI 및 차트 배치 구조 (세션 탭 구성, 밴드 차트와의 화면 관계, 미개방 세션의 표시 방식)
       2. 시간 감쇠 반감기의 구체적 수치, 완만한 감쇠 외에 "최근 N개월 이내 신호만 유효"라는 하드 컷오프를 병용할지 여부
       3. 사용자 1인당 신호 총량 상한의 구체적 수치 및 산정 단위(일 단위 상한 / 동시 유지 활성 신호 수 상한)
       4. 신호 종류별 상대 가중치 (조화 판단에서 나온 신호와 추천 결과 선택 로그의 비중) — 조화 판단 기능 설계 이후 논의
       5. 조화 판단 기능 자체의 설계
       6. 세션 세분화 여부 (기타의 일렉/어쿠스틱 구분 등). v1은 5종 대분류로 진행
       7. 자격 하한선을 비율 기반으로 전환하는 시점 및 비율값
   
   12. 리스크 및 대응
   
       | 리스크 | 대응 |
       |---|---|
       | 표본이 적은 세션의 차트가 장기간 열리지 않음 | 정책적으로 수용. 급조된 차트보다 지연을 택함. 필요 시 세션별 하한선 재검토 |
       | 소수의 열성 사용자가 순위를 좌우 | 서로 다른 사용자 5명 자격 게이트 + 1인당 신호 총량 상한 |
       | 유행이 지난 곡이 상위에 고착 | 순위 점수에 시간 감쇠 적용 |
       | 단순 호기심을 연주 의사로 오인 | 의도가 담긴 액션(추천 결과 선택, 조화 판단 요청)만 신호로 인정. 단순 조회는 제외 |
       | 세션 태그 누락으로 신호 사용 불가 | 신호 발생 지점 전반에 세션 태그 기록을 스키마 요구사항으로 명시 |
       | 밴드 차트와 세션 차트의 신호 혼선 | 신호 발생 화면(개인/단체방) 기준 라우팅 원칙을 단일 규칙으로 유지 |
4. **애플리케이션 픽**
   - 애플리케이션에서 연주할 만한 밴드 곡들을 선별하여 순위를 매긴 차트. 어떻게?

### 2. 개인화 곡 추천
1. **세션별 추천**
   1. **보컬**
      - 음역대. 모른다면 어떻게 할지에 대한 고민 필요
      - 성별 및 보컬 톤
      - 가능한 언어
      - 기타 아이디어
   2. **기타**
      - 가지고 있는 기타의 종류(일렉, 통기타, 클래식기타)
      - 튜닝 변경 가능 여부
      - 테크닉의 수준
      - 혼자 하는 곡을 추천하는 거니까 기타 파트를 묻지는 않아도 될듯
      - 기타 아이디어
   3. **베이스**
      - 보유중인 악기의 현 개수
      - 선호하는 주법(핑거 피킹, 피크 피킹, 슬랩)
      - 기타 아이디어
   4. **드럼**
      - 페달 주법
      - 템포, 박자 한계
      - 기타 아이디어
   5. **키보드**
      - 건반의 갯수(몇키인지)
      - 키보드의 종류(전자피아노, 신디사이저 등)
      - 기타 아이디어
2. **LLM 자연어 검색을 통한 곡 추천**
   1. 프롬프트를 입력하는 칸에 가이드 문구를 삽입
      - 예를 들어 *‘나는 일렉기타를 연주하는데 일렉기타 솔로가 돋보이고 난이도는 평이한 곡을 연주해보고 싶어.’* 처럼 문구를 작성해놓는 거야.
   2. 프롬프트 입력 후 처리 방법 (정확한 방법 수립해야 함)
      - **파라미터 추출**: LLM이 프롬프트에서 `'분위기(Summer, Refreshing)'`, `'난이도 제약(Drum <= Level 2)'`, `'악기 강조(Guitar Solo >= Level 4)'`를 JSON 형태로 파싱.
      - **DB필터링 및 벡터 검색**: 메타데이터 필터로 곡 풀을 1차 선별한 후, 분위기 임베딩(Vector Similarity)을 적용해 최종 리스트를 반환

### 5. 기타 기능
1. **곡을 추천 시 참고 가능한 악보의 선택지들을 보여주는 기능**
   - 유료 악보 사이트: 악보바다, 악보공장, 마이뮤직시트의 검색 결과 URL 딥링크(Deep Link) 연동.
   - 코드/TAB: 얼티밋기타(Ultimate Guitar), 코드위키 링크 연동.
   - 연주 영상: 유튜브 API를 통해 `[곡명 + 악기명 + 커버/강좌]` 검색 결과를 인앱 웹뷰나 외부 링크로 바로 매핑.
2. **합주 녹음 및 기기간 메트로눔 타이밍 동기화**
   1. **합주 녹음 기능**
      - 녹음을 위한 기능이 아닌 자신만 합주 시의 녹음을 듣기 위한 기능이므로 트랙 작업 걱정을 할 필요 없음.
   2. **기기간 메트로눔 타이밍 동기화**
      - **시각적, 청각적 매트로눔 기능**:
        - 매트로눔 설정 시 화면이 깜빡거리는 것으로 타이밍 알려주는 기능
        - 화면이 깜빡일 때마다 청각적으로 매트로눔 소리를 출력하지만 기기 동기화 시에는 소리를 제거 (오디오 지연 현상)
        - 합주 시 세션 간의 기기가 동기화되어 같은 타이밍에 화면이 깜빡이도록 설정 (BPM은 같지만 원하는 깜빡임 정도는 다를 것 같음)
